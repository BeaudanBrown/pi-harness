# Managed Matrix sessions

Managed sessions are enabled atomically with `services.pi-harness.managedSessions.enable`. One lingered user relay owns the Matrix access token, `/sync`, host Space, coordinator room, project Spaces, room lifecycle, durable queues, and transcript projection. Pi adapters receive only a private peer-UID-checked socket and an attachment nonce. Disabled hosts expose no relay service, adapter, lifecycle/checkpoint tools, status command, socket configuration, or Matrix environment.

## Layout and behavior

The coordinator is the stable, non-deletable `default/coordinator` conversation. Coordinator tools list configured depth-one workspaces, create one absent immediate-child local Git project, and start, resume, stop, or bridge-delete project conversations. It disables built-in tools, context, and discovered resources before loading only its lifecycle profile. A project process runs in a dedicated managed tmux window under its workspace root session. Its profile is the normal engineering profile minus local TUI/viewer, Pi-R, and AgentGraph resources, so web search, GitHub issue workflows, delegated checks/reviews, browser and architecture workflows, and trusted project extensions, skills, prompts, and context remain available over Matrix. Selecting a `local-llm/*` model dynamically narrows active engineering tools to the intersection with the declarative `pi-local` allowlist (`read`, `bash`, `edit`, `write`, `grep`, `find`, and `ls`); connected `remote_checkpoint` and `remote_artifact_export` transport tools remain available. Switching to another provider restores the prior managed-project tools while preserving the relay's current connected/disconnected tool state. A fail-closed tool-call hook blocks any stale disallowed local-model call. This is a model-facing capability policy, not the complete `pi-local` launch profile and not a security sandbox: managed extensions, skills, prompts, project context, and the broad host authority of `bash`, `edit`, and `write` remain loaded. Launch is a fixed host-owned `tmux_project` operation and a trusted `direnv exec <canonical-cwd> pi`; callers cannot supply shell, argv, paths, PIDs, tmux targets, or environment. Project creation accepts only a configured root key, safe child name, and immutable concept. The launcher creates no scaffold, task, remote, or publication: it creates the directory, initializes local Git on `main`, and records the creation key in local Git metadata. A private host intent plus deterministic staging and that key makes explicit retries deterministic, while foreign existing paths, Git metadata links, and symlinks fail unchanged. The empty Pi session and each Matrix provisioning phase are persisted before the next boundary; deterministic private room aliases reconcile an uncertain create response instead of duplicating Spaces or rooms. The result includes a bounded room link, and Pi's `--approve` applies project trust only to that managed run without writing global trust state.

Each conversation owns one private Matrix room. The host Space contains the coordinator and host-resolved project Spaces. For Git repositories, a harness-owned authority wrapper around the configured tmux launcher validates its canonical checkout result, the checkout top level, and Git common directory, then derives one stable project key shared by the main checkout and its linked worktrees; checkout identity remains in each room name. Non-Git immediate-child workspaces receive a stable fallback identity. Project keys—not caller paths, display names, or Space IDs—select deterministic private Matrix Space aliases, so identical names cannot merge repositories and repeated or uncertain starts reuse one Space. Compatibility manifests without this identity remain untouched until explicit reconciliation; ordinary startup and the status command report only an aggregate pending count and never silently reparent rooms. Ordinary authorized text is an idle prompt or busy follow-up. Typed controls are `!help`, `!status`, `!model [provider/model|filter]`, `!thinking [level]`, `!compact [focus]`, `!new`, `!stop`, `!abort`, and `!steer <text>`; malformed or unknown `!` commands show bounded help and never become prompts. Model and thinking choices are limited to the session's authenticated scope and use single-select polls of at most 20 answers, with provider/filter narrowing for larger catalogues. Question checkpoints with declared options use single-select polls with opaque, checkpoint-bound answer IDs; the first valid operator vote resumes the conversation with the exact declared option. An ordinary authorized text answer atomically retires the poll and resumes with that text instead. Optionless questions, blocked boundaries, and issue-completion boundaries remain notices. Model, thinking, compaction, and context-reset controls reject a busy adapter without altering its run. Adapter-executed controls and slash commands hold an ephemeral Matrix typing lease until their durable result or completion; leases are reference-counted with model activity, so one completion cannot clear feedback for concurrent work. Compaction uses Pi's native history-preserving compactor and reports measured context before and after. Context reset is confirmation-gated: `!new` explains the preserved-history boundary and exact `!new --confirm` creates a fresh Pi session generation without model-visible input. The new session and binding boundary are durable before activation; the room, workspace, concept, selected model/thinking, status metadata, and prior terminal-only Pi session files are preserved. A valid reply to a bot event strips Matrix's fallback quotation. Authorized unencrypted Element X JPEG, PNG, and WebP image messages are downloaded only by the credential-owning relay. A caption is prompt text; an image without a caption is delivered immediately with a neutral prompt. The adapter injects the prompt and image as one ordered Pi user turn. A model without image input support rejects the entire turn, posts a clear room notice, and does not switch models or fall back to caption-only input. The managed-only `remote_artifact_export` tool intentionally sends one workspace-relative image, audio file, or generic file without a separate approval prompt. It rejects traversal, hidden/control and sensitive path segments, symlinks, special files, types outside a conservative image/audio/text/JSON/PDF/ZIP allowlist, active or executable content, malformed media, and files over 25 MiB before any bytes cross IPC. Outbound images and audio pass bounded structural container validation before transfer; the generic-file allowlist does not silently downgrade malformed media. Tool activity exposes only `remote_artifact_export`; file contents and host paths are never projected. Edits, reactions, threads, generic inbound attachments, voice input, encrypted/unsupported media, malformed relations, foreign senders/rooms, stale initial events, and oversized payloads fail closed.

The relay checks declared and streamed byte lengths, response and signature MIME agreement, decodability, declared and decoded dimensions, a 16,384-pixel side limit, and a 40-megapixel bound. ImageMagick selects the first frame, applies orientation, strips metadata, and rewrites the supported format before the relay commits it. The private content-addressed host spool permits at most 128 blobs, 25 MiB each, and 256 MiB total. Atomic digest-verified commits and typed per-chunk digests keep paths and credentials out of IPC. Live pending-delivery references are retained across relay or adapter interruption; completed, rejected, expired, partial, and unreferenced data is removed idempotently without deleting recovery state.

Only persisted transcript entries after the binding boundary are mirrored. Matrix-origin users are not echoed. Terminal-origin users are labelled; final assistant text and explicit `remote_checkpoint` question, blocked, and issue-completion boundaries are projected as bounded sanitized Markdown with plain fallback.

During each complete busy span, the relay maintains Matrix typing and one edited activity card. The card exposes only collapsed tool names and running/completed/error states. At settlement it becomes an unpinned, immutable snapshot with measured duration, model/thinking, generation, balanced context usage, run tokens/turns, tool totals/errors/counts, compactions, and completion outcome; unavailable measurements are omitted. This snapshot is persisted before the final assistant answer is projected. Thinking, arguments, paths, commands, tool output, partial assistant text, reasoning, and internal entries remain local.

A managed `/aloop` invocation uses a dedicated durable lifecycle channel instead of projecting the supervisor's ordinary final answers. Matrix receives one bounded startup notice with the epic, selected child, shared budget, launch cap, and supervisor/implementation, patch, and review models. Later notices are limited to recovery, settled attempt, checkpoint, bounded stop, cancellation, startup failure, and epic-ready outcomes. Activity cards collapse every nested worker, review, patch, diagnostic, and verification operation to the single name `aloop`; raw tool names, progress/heartbeat streams, local paths, markers, logs, receipts, and spool identifiers remain local. Lifecycle notices use stable relay projection identities and replay after reconnect without duplication. `!abort` aborts the Pi turn and its inherited worker process signal before aloop deactivates, prevents subsequent lifecycle effects, and retains committed and local recovery state. A settled invocation always requires a new explicit `/aloop` command; it does not continue across turns automatically.

Stop cancels unfinished input and terminates only the exact persisted managed window, preserving the room, manifest, Pi history, workspace, and files. Confirmed bridge deletion removes Matrix/relay binding state but preserves Pi history and project state. Managed `!new --confirm` is the only context-reset path: it appends and activates one new generation, while historical generations have no Matrix list, switch, resume, or reactivation interface. Local `/new` and `/fork` stay unbound; exact `/resume` reattaches only a previously bound active-generation session.

## Existing-room reconciliation

Run reconciliation from the coordinator conversation only:

1. Call `remote_project_reconcile_preview`. This resolves every compatibility checkout through the trusted launcher, validates current room and Space authority, and returns a bounded plan plus a stable reconciliation key. It performs no Matrix or manifest mutation.
2. Review the listed conversation, workspace, project, and checkout display identities. If any checkout was removed, inaccessible, or changed ownership, restore or resolve it first; the conversation and room remain unchanged.
3. Call `remote_project_reconcile_apply` with the exact preview key and `confirm: true`. A private durable intent is written before Matrix changes. Existing room IDs are linked into their deterministic project Spaces, manifests gain only host-resolved project identity, and old parent links are removed. Pi session files, bindings, active/dormant state, pending input/control/projection state, and workspace files are not rewritten.
4. If interrupted, repeat apply with the same key. The relay resumes target-Space creation/lookup, host linking, room linking, atomic manifest replacement, or old-parent unlinking from the last durable phase. Do not delete or edit the reconciliation intent.
5. Review the returned obsolete-Space count. Cleanup is optional and separately destructive: call `remote_project_space_cleanup` with the same key and `confirm: true`. It refuses any referenced, non-empty, inaccessible, wrong-type, or insufficiently bot-controlled Space. For a verified empty obsolete Space it removes the host link, removes the operator from that obsolete Space, and then makes the bot leave. It never leaves a current conversation room or touches a checkout.

Reconciliation is forward-recoverable but not transactionally rollbackable across Matrix and synchronized manifests. Before cleanup, the durable intent retains old parent IDs, but there is no automatic rollback operation. A room linked to its target before interruption can temporarily have both old and new parents; retry completes the move. After confirmed cleanup, an obsolete Space is intentionally no longer accessible to the operator or bot. Back up synchronized manifests and host-local registry state before deployment-level work; the final V2 store migration remains owned by #63.

Removing a checkout or Git worktree never deletes its managed conversation or Matrix room: resolution fails closed and leaves the durable binding visible. Confirmed bridge deletion keeps its existing independent behavior—it removes the room/binding but never invokes checkout or worktree removal.

## Health and recovery

Run as the configured relay user:

```sh
pi-managed-session-status
systemctl --user status pi-managed-session-relay.service
journalctl --user -u pi-managed-session-relay.service --since today
```

The status command fails unless the service is active, its private socket exists, and durable registry and manifest JSON are readable. Its JSON output contains only aggregate lifecycle states, cursor presence, and `pendingProjectReconciliation` count—not tokens, room IDs, event IDs, message text, paths, or launch errors.

The relay uses bounded exponential backoff with jitter, honors Matrix `retry_after_ms`, and cancels waits on shutdown. Media is fetched through Matrix's authenticated client media endpoint; access tokens never enter media URLs, spool metadata, IPC, or Pi history. Stable Matrix transaction IDs make uncertain transcript, activity-card edit, checkpoint poll/notice, poll closure, notice, command-acknowledgement, and artifact-event retries idempotent. Typing is intentionally ephemeral and reconstructed only from live durable controls, command deliveries, or activity spans; it is never persisted as authoritative state. Artifact bytes cross IPC only as digest-verified bounded chunks, enter the private bounded spool, and use a durably recorded, expiry-bounded MXC reservation before retry-safe upload and room send; restart resumes the last durable phase and removes consumed local blobs. A crash in the create-response window can leave only an empty server-expiring reservation—never uploaded bytes—and durable export count plus spool quotas bound local recovery state. Checkpoint poll publication intent, exact answer mapping, event identity, and active/retired state are persisted before cursor advancement, so restart recovery preserves the hard boundary and cannot accept changed, duplicate, foreign, malformed, late, or post-close votes. Registry writes are private atomic write/fsync/rename operations. After relay restart, adapters may reattach during the reconciliation grace period; unmatched conversations become dormant. Accepted input, expanded input, persisted unfinished turns, checkpoints, and final projections resume from durable identity. Explicit stop/abort cancellation is terminal and is never recovered.

Cursor state is explicit: a fresh relay performs one bootstrap sync, persists its returned cursor, and does not execute retained timeline commands from that bootstrap response. Established state requires a bounded cursor; malformed state and limited/oversized timeline gaps do not advance it. Authentication failures are concise HTTP diagnostics in the user service journal. Do not delete or hand-edit `registry.json`; restore the last known complete synchronized manifests and host-local registry together, or resolve the conflict explicitly. Legacy `.remote-session` files and rooms are never scanned or migrated.

## Token rotation and device revocation

Rotation does not rebuild Pi sessions, recreate rooms, or clear registry/projection state:

1. Create a replacement Matrix login/device for the same configured bot MXID.
2. Atomically replace the SOPS-rendered credential file with exactly one `PI_MATRIX_ACCESS_TOKEN=<new-token>` assignment, owned by the relay user and mode `0400` or `0600`.
3. Restart and verify:

   ```sh
   systemctl --user restart pi-managed-session-relay.service
   pi-managed-session-status
   journalctl --user -u pi-managed-session-relay.service -n 50
   ```

4. Send one message to an existing managed room and confirm its normal projection.
5. Revoke the old Matrix device only after the replacement is healthy.

The launcher reads the credential file on every service start. Never put the token in Nix, shell arguments, tmux, Pi settings/session metadata, issue comments, test fixtures, or diagnostic commands. Errors and bounded diagnostics redact credential-like environment values and never include Matrix response bodies.

## Troubleshooting

- **Service inactive:** inspect the user journal and credential owner/mode. Confirm linger is enabled and network-online is available.
- **HTTP 401/403:** replace or rotate the token and confirm the configured bot MXID did not change.
- **Repeated rate limits/outage:** leave the service running; bounded retry preserves cursor and stable transactions without duplicate turns.
- **Dormant room:** ordinary text queues and wakes the exact persisted session. Dormant steer/abort intentionally do not wake it.
- **Launch failure:** verify the configured workspace root, immediate-child workspace, direnv policy, and `tmux_project` managed operations. Error output is intentionally concise and redacted.
- **Image rejected:** confirm the active model advertises image input and resend after selecting a capable model. For size, format, or decode rejection, re-export a bounded JPEG, PNG, or WebP; the relay never sends only the caption.
- **Media spool quota:** let completed/expired deliveries and artifact exports clean up, then restart the relay. Never delete blob metadata referenced by a live pending input/export or hand-edit `registry.json`.
- **Artifact rejected:** pass a path relative to the workspace root, not the conversation's relative cwd. Hidden/control or sensitive paths, symlinks, special files, executable/active content, malformed media, and files over 25 MiB are deliberately unavailable.
- **Malformed durable state:** stop the service and reconcile the complete manifest/runtime pair; temporary or legacy files are not recovery sources.

## Deferred scope

The current staged protocol deliberately excludes cross-host discovery, migration or failover; shared-room claims; inbound audio/video, encrypted media, generic inbound attachments, edits, reactions, and threads; container/sandbox isolation beyond the service and fixed launcher boundary; automatic project conflict prevention; idle process retirement; and import of legacy direct-bridge rooms or state.
