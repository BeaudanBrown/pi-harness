# Managed Matrix sessions

Managed sessions are enabled atomically with `services.pi-harness.managedSessions.enable`. One lingered user relay owns the Matrix access token, `/sync`, host Space, coordinator room, project Spaces, room lifecycle, durable queues, and transcript projection. Pi adapters receive only a private peer-UID-checked socket and an attachment nonce. Disabled hosts expose no relay service, adapter, lifecycle/checkpoint tools, status command, socket configuration, or Matrix environment.

## Layout and behavior

The coordinator is the stable, non-deletable `default/coordinator` conversation. The relay pins `TMUX_TMPDIR` to `XDG_RUNTIME_DIR`, so host-managed windows and the operator's existing `tmux_project` launcher always address the same per-user tmux server. The launcher keeps its ordinary project session/path entries and additionally lists every live window carrying a valid managed-conversation marker; selecting that entry switches the requesting client to the exact existing Pi window and never starts, resumes, duplicates, or sends keys to a process. Dormant conversations have no live window and therefore remain visible through managed lifecycle/status interfaces rather than the tmux launcher. Coordinator tools list configured depth-one workspaces and host-validated Git worktrees; create an absent local Git project or a linked worktree; optionally pair worktree creation or cleanup with conversation lifecycle; and independently start, resume, stop, or bridge-delete project conversations. It disables built-in tools, context, and discovered resources before loading only its lifecycle profile. A project process runs in a dedicated managed tmux window under its workspace root session. Its profile is the normal engineering profile minus local TUI/viewer, Pi-R, and AgentGraph resources, so web search, GitHub issue workflows, delegated checks/reviews, browser and architecture workflows, and trusted project extensions, skills, prompts, and context remain available over Matrix. Selecting a `local-llm/*` model dynamically narrows active engineering tools to the intersection with the declarative `pi-local` allowlist (`read`, `bash`, `edit`, `write`, `grep`, `find`, and `ls`); connected `remote_checkpoint` and `remote_artifact_export` transport tools remain available. Switching to another provider restores the prior managed-project tools while preserving the relay's current connected/disconnected tool state. A fail-closed tool-call hook blocks any stale disallowed local-model call, including `run_worker`, `review_agents`, and Aloop worker capabilities that could delegate work to another model. This is a model-facing capability policy, not the complete `pi-local` launch profile and not a security sandbox: managed extensions, skills, prompts, project context, and the broad host authority of `bash`, `edit`, and `write` remain loaded. The generated managed-project runtime explicitly supplies Bash and its discovery helper so Pi's built-in `bash` tool does not fall back to an absent `sh` on NixOS. Launch is a fixed host-owned `tmux_project` operation and a trusted `direnv exec <canonical-cwd> pi`; callers cannot supply shell, argv, paths, PIDs, tmux targets, or environment. Project creation accepts only a configured root key, safe child name, and immutable concept. The launcher creates no scaffold, task, remote, or publication: it creates the directory, initializes local Git on `main`, and records the creation key in local Git metadata. A private host intent plus deterministic staging and that key makes explicit retries deterministic, while foreign existing paths, Git metadata links, and symlinks fail unchanged. The empty Pi session and each Matrix provisioning phase are persisted before the next boundary; deterministic private room aliases reconcile an uncertain create response instead of duplicating Spaces or rooms. The result includes a bounded room link, and Pi's `--approve` applies project trust only to that managed run without writing global trust state.

Each conversation owns one private Matrix room. The host Space contains the coordinator and host-resolved project Spaces. For Git repositories, a harness-owned authority wrapper around the configured tmux launcher validates its canonical checkout result, the checkout top level, and Git common directory, then derives one stable project key shared by the main checkout and its linked worktrees; checkout identity remains in each room name. Non-Git immediate-child workspaces receive a stable fallback identity. Project keys—not caller paths, display names, or Space IDs—select deterministic private Matrix Space aliases, so identical names cannot merge repositories and repeated or uncertain starts reuse one Space. Compatibility manifests without this identity remain untouched until explicit reconciliation; ordinary startup and the status command report only an aggregate pending count and never silently reparent rooms. Every currently joined room member other than the relay bot and exact configured ignored service-account MXIDs has equal authority. This includes joined Signal/Facebook bridge puppet identities. The relay checks one bounded current membership snapshot before acceptance, persists the sender MXID before cursor advancement, and includes it in ordinary model-visible attribution. Leading-slash commands preserve native Pi command/template dispatch while retaining durable sender provenance. Matrix invitations, removals, bans, and power levels remain outside relay control. Ordinary authorized text is an idle prompt or steering input for the active run, not a queued follow-up. Busy image messages likewise steer with their caption and image together; recovered expanded ordinary input uses the same policy. Explicit legacy follow-up deliveries retain follow-up semantics. Typed controls are `!help`, `!status`, `!model [provider/model|filter]`, `!thinking [level]`, `!compact [focus]`, `!new`, `!stop`, `!abort`, and `!steer <text>`; malformed or unknown `!` commands show bounded help and never become prompts. Model and thinking choices are limited to the session's authenticated scope and use single-select polls of at most 20 answers, with provider/filter narrowing for larger catalogues. Control-selection and option-bearing checkpoint poll starts carry a deterministic Matrix room mention to request a notification from each participant whose client and room push settings permit it; poll closures do not notify. Successful exact `!model provider/model` and `!thinking level` selections are persisted as current conversation preferences before the control is acknowledged, so subsequent turns, relay restarts, managed-process stop/resume, host restarts, and fresh generations restore both choices until another exact selection succeeds. The host-owned launcher validates and forwards these optional values to both project and coordinator windows; it also verifies the relay's workspace path against its own canonical workspace resolution before injecting that path. Filter and poll-opening controls do not change preferences, rejected or mismatched results cannot mutate them, interrupted exact model mutations are safely reapplied from their durable control identity, and uncertain interrupted thinking mutations remain conservative rather than being guessed. Existing conversations without stored preference metadata retain their prior launch behavior until each exact selection succeeds once. Question checkpoints with declared options use single-select polls with opaque, checkpoint-bound answer IDs. The first valid currently joined participant vote resumes the conversation with the exact declared option. An ordinary authorized text answer atomically retires the poll and resumes with that text instead. Optionless questions, blocked boundaries, and issue-completion boundaries remain notices. Model, thinking, compaction, and context-reset controls reject a busy adapter without altering its run. Adapter-executed controls and slash commands hold an ephemeral Matrix typing lease until their durable result or completion; leases are reference-counted with model activity, so one completion cannot clear feedback for concurrent work. Compaction uses Pi's native history-preserving compactor and reports measured context before and after. Context reset is confirmation-gated: `!new` explains the preserved-history boundary and exact `!new --confirm` creates a fresh Pi session generation without model-visible input. The new session and binding boundary are durable before activation; the room, workspace, concept, selected model/thinking, status metadata, and prior terminal-only Pi session files are preserved. A valid reply to a bot event strips Matrix's fallback quotation. Authorized unencrypted Element X JPEG, PNG, and WebP image messages are downloaded only by the credential-owning relay. A caption is prompt text; an image without a caption is delivered immediately with a neutral prompt. The adapter injects the prompt and image as one ordered Pi user turn. A model without image input support rejects the entire turn, posts a clear room notice, and does not switch models or fall back to caption-only input. The managed-only `remote_artifact_export` tool intentionally sends one workspace-relative image, audio file, or generic file without a separate approval prompt. It rejects traversal, hidden/control and sensitive path segments, symlinks, special files, types outside a conservative image/audio/text/JSON/PDF/ZIP allowlist, active or executable content, malformed media, and files over 25 MiB before any bytes cross IPC. Outbound images and audio pass bounded structural container validation before transfer; the generic-file allowlist does not silently downgrade malformed media. Tool activity exposes only `remote_artifact_export`; file contents and host paths are never projected. Edits, reactions, threads, generic inbound attachments, voice input, encrypted/unsupported media, malformed relations, foreign senders/rooms, stale initial events, and oversized text/event/IPC-frame payloads fail closed; supported inbound images have no aggregate byte-size cap.

Inbound images pass through unchanged. Matrix image-event metadata is extensible: mentions, animation flags, thumbnails and future optional fields do not block delivery. The relay reads only the media URL and plain caption fields; size, dimensions and declared MIME hints are optional and ignored, without coercion. A missing/empty body or a body equal to the filename uses the neutral image prompt; a distinct body with a filename remains a caption. Known encrypted-file, relation/thread and edit markers are still explicitly excluded, and sender/room checks are unchanged. Actual unsupported image formats are reported through the normal rejection path rather than silently filtered by declared MIME metadata. The relay ignores declared size and dimensions, does not impose a download-byte or pixel cap, and does not decode, strip metadata, flatten animation or re-encode images. HTTP framing and decompression belong to the HTTP client; genuine download failures are reported. Empty responses and unsupported image formats are rejected. A signature check identifies JPEG, PNG or WebP and supplies the actual MIME type to the model instead of trusting event/HTTP MIME metadata; full image decoding remains the model's responsibility. Actual byte counts and digests describe internal transfer integrity, not an image admission policy; required legacy dimension fields use neutral placeholders and are not passed to the model. The private content-addressed host spool permits at most 128 live blob records. Inbound-marked blobs are exempt from byte quotas; outbound artifacts retain the 25 MiB per-file and 256 MiB aggregate byte restrictions. Matrix/provider limits and available process memory/disk still apply; this is not a guarantee of unlimited resource capacity. Atomic digest-verified commits and typed per-chunk digests keep paths and credentials out of IPC. Live pending-delivery references are retained across relay or adapter interruption; completed, rejected, expired, partial, and unreferenced data is removed idempotently without deleting recovery state.

Only persisted transcript entries after the binding boundary are mirrored. Matrix-origin users are not echoed; their verified MXIDs remain attached to durable input provenance and ordinary model-visible text/image captions. Terminal-origin users are labelled; final assistant text and explicit `remote_checkpoint` question, blocked, and issue-completion boundaries are projected as bounded sanitized Markdown with plain fallback. The checkpoint tool advertises one flat, bounded object schema for llama.cpp constrained-decoding compatibility, then applies the stricter kind-specific exact-field validation before any durable marker or Matrix side effect.

During each complete busy span, the relay maintains best-effort Matrix typing and one edited activity card. Typing requests are single-flight per conversation, coalesce newer intent, and have a five-second deadline; active typing refreshes every twenty seconds. They never gate durable work and are cancelled on relay shutdown. Network outages can still cause the homeserver's typing timeout to expire. After ten seconds of attachment loss, the old card is finalized as interrupted. A surviving adapter immediately replays activity on reconnect; if the relay reports that interruption, the adapter uses a deterministic continuation card, retaining run counters without injecting a model turn or rewriting the old snapshot. The card exposes only collapsed tool names and running/completed/error states. At settlement it becomes an unpinned, immutable snapshot with measured duration, model/thinking, generation, balanced context usage, run tokens/turns, tool totals/errors/counts, compactions, and completion outcome; unavailable measurements are omitted. This snapshot is persisted before the final assistant answer is projected. Thinking, arguments, paths, commands, tool output, partial assistant text, reasoning, and internal entries remain local.

Activity settlement is single-flight: the adapter detaches a closing span before asynchronous transcript work, freezes its final statistics, and retries the exact final activity ID/revision/payload until acknowledged. Reconnect replays a pending final rather than resurrecting it as busy; only an authoritative interrupted-card response permits a continuation identity. A newer run owns a separate active span, which an older acknowledgment cannot clear. Pending finalizations keep idle refresh busy, and final-answer projection waits for closing feedback. Retry uses the existing projection backoff even when the IPC connection survives a failure. At most 32 closing snapshots are retained; saturation omits new activity cards, not model execution, and normal feedback resumes after the backlog drains. These snapshots are adapter-session-local: process exit or session switch retains the existing relay interruption/recovery behavior, not a new durable adapter journal.

A managed `/aloop` invocation uses a dedicated durable lifecycle channel instead of projecting the supervisor's ordinary final answers. Matrix receives one bounded startup notice with the epic, selected child, shared budget, launch cap, and supervisor/implementation, patch, and review models. Later notices are limited to recovery, settled attempt, checkpoint, bounded stop, cancellation, startup failure, and epic-ready outcomes. Activity cards collapse every nested worker, review, patch, diagnostic, and verification operation to the single name `aloop`; raw tool names, progress/heartbeat streams, local paths, markers, logs, receipts, and spool identifiers remain local. Lifecycle notices use stable relay projection identities and replay after reconnect without duplication. `!abort` aborts the Pi turn and its inherited worker process signal before aloop deactivates, prevents subsequent lifecycle effects, and retains committed and local recovery state. A settled invocation always requires a new explicit `/aloop` command; it does not continue across turns automatically.

Stop cancels unfinished input and terminates only the exact persisted managed window, preserving the room, manifest, Pi history, workspace, and files. Confirmed bridge deletion removes Matrix/relay binding state but preserves Pi history and project state. Managed `!new --confirm` is the only context-reset path: it appends and activates one new generation, while historical generations have no Matrix list, switch, resume, or reactivation interface. Local `/new` and `/fork` stay unbound; exact `/resume` reattaches only a previously bound active-generation session.

## Coordinator refresh

`remote_session_refresh` is a coordinator-only, confirmation-gated operation for
one existing **project** conversation. Pass its conversation ID and `confirm: true`.
It re-resolves host placement and restarts Pi with the installed launcher and
configuration, preserving the room, session file and active generation, history,
model/thinking preferences, checkpoint state, and accepted queued input. It does
not create a new generation, rebuild Nix packages, upgrade the running relay, or
restart the coordinator itself.

Refresh refuses busy, starting, transitioning, or unsettled conversations. The
relay pauses delivery while an authenticated live adapter checks Pi's idle state
and queued work. Only that idle adapter requests graceful shutdown; refresh never
aborts it. The host waits for disconnection before clearing the exact old window
and launching the same session. New Matrix input stays durably queued during this
interval. An unresponsive or old adapter that cannot confirm idle, or an unattached
window of unknown activity, is refused rather than force-killed.

A failed relaunch leaves the session and queue intact. Repeat refresh (or resume)
after resolving configuration. If the relay crashes during refresh, normal
attachment/restart reconciliation applies; repeat the operation explicitly if
needed. A host update must deploy matching relay/adapter packages before this
operation can be used; refreshing does not patch already-running old adapters.

## Coordinator-managed Git worktrees

Worktree authority remains behind typed coordinator requests and the harness-owned launcher wrapper; the coordinator receives no shell, arbitrary path, generic Git, GitHub, or Matrix capability. Select a Git checkout that is an immediate child of a configured root, name an explicit existing base ref, and provide a new branch. The host accepts only one unambiguous local branch, remote-tracking ref, or tag, peels it to a commit, validates the repository's owned main checkout and common Git directory, and derives a sibling name such as `project-feature-example-71ada2fb`. The branch slug is bounded and the digest prevents truncation or normalization collisions. Existing branches, paths, registrations, symlinks, root escapes, arbitrary revisions, and ambiguous refs fail unchanged.

The coordinator operations are:

1. `remote_worktree_list` reports root/linked identity, branch and commit, main-checkout status, clean/locked state, bound conversation IDs, and durable creation/removal phases for one project.
2. `remote_worktree_create` creates only the local branch and linked checkout. `remote_worktree_conversation_create` performs the same worktree operation and then creates an empty Pi session and room in the project's existing stable Space. The objective must be sent later in that resulting room.
3. `remote_worktree_remove_preview` records an independent removal snapshot. `remote_worktree_cleanup_preview` records the same snapshot for a selected conversation and indicates active use. Both may accept an explicit merge target but perform no mutation.
4. `remote_worktree_remove_apply` with the exact removal key and `confirm: true` removes only a still-matching clean, unlocked, inactive linked worktree. It leaves all conversations and the local branch intact.
5. `remote_worktree_cleanup_apply` stops only the selected exact process, removes the linked worktree, and invokes existing bridge deletion. Other dormant conversations for that missing checkout remain preserved and visible. Pi files, commits, the branch, and Matrix server history remain.
6. `remote_worktree_branch_delete` is always separate and confirmed. It deletes only the unchanged local branch after checkout removal when it is checked out nowhere and was previewed as fully merged into the unchanged explicit target. Omitting a merge target preserves the branch.

Creation and cleanup intents are private, atomic, bounded, and serialized per Git common directory. If creation is interrupted after branch or checkout creation, repeat the identical operation; the launcher reuses only the exact recorded artifacts. If bundled creation fails during Pi or Matrix provisioning, the worktree remains and existing session/room intents resume forward. If bundled cleanup is interrupted after stop, worktree removal, or bridge deletion, repeat apply with the same key. Never rename, move, unlock, prune, edit, or delete the branch/worktree/intent while recovery is pending; changed state fails closed instead of being guessed or forced.

## Existing-room reconciliation

Run reconciliation from the coordinator conversation only:

1. Call `remote_project_reconcile_preview`. This resolves every compatibility checkout through the trusted launcher, validates current room and Space authority, and returns a bounded plan plus a stable reconciliation key. It performs no Matrix or manifest mutation.
2. Review the listed conversation, workspace, project, and checkout display identities. If any checkout was removed, inaccessible, or changed ownership, restore or resolve it first; the conversation and room remain unchanged.
3. Call `remote_project_reconcile_apply` with the exact preview key and `confirm: true`. A private durable intent is written before Matrix changes. Existing room IDs are linked into their deterministic project Spaces, manifests gain only host-resolved project identity, and old parent links are removed. Pi session files, bindings, active/dormant state, pending input/control/projection state, and workspace files are not rewritten.
4. If interrupted, repeat apply with the same key. The relay resumes target-Space creation/lookup, host linking, room linking, atomic manifest replacement, or old-parent unlinking from the last durable phase. Do not delete or edit the reconciliation intent.
5. Review the returned obsolete-Space count. Cleanup is optional and separately destructive: call `remote_project_space_cleanup` with the same key and `confirm: true`. It refuses any referenced, non-empty, inaccessible, wrong-type, or insufficiently bot-controlled Space. For a verified empty obsolete Space it removes the host link, removes the operator from that obsolete Space, and then makes the bot leave. It never leaves a current conversation room or touches a checkout.

Reconciliation is forward-recoverable but not transactionally rollbackable across Matrix and synchronized manifests. Before cleanup, the durable intent retains old parent IDs, but there is no automatic rollback operation. A room linked to its target before interruption can temporarily have both old and new parents; retry completes the move. After confirmed cleanup, an obsolete Space is intentionally no longer accessible to the operator or bot. Back up synchronized manifests and host-local registry state before deployment-level work; the final V2 store migration remains owned by #63.

Removing a checkout or Git worktree independently never deletes its managed conversation or Matrix room: resolution fails closed and leaves the durable binding visible. Confirmed bridge deletion keeps its existing independent behavior—it removes the room/binding but never invokes checkout or worktree removal. Only the separately named bundled cleanup operation deliberately composes exact stop, worktree removal, and that unchanged bridge-deletion primitive.

## Health and recovery

Run as the configured relay user:

```sh
pi-managed-session-status
systemctl --user status pi-managed-session-relay.service
journalctl --user -u pi-managed-session-relay.service --since today
```

The host status command fails unless the service is active, its private socket exists, and persistent registry and manifest state are readable. It also exits nonzero when sync is starting, blocked, or its last successful cursor commit is at least 120 seconds old (or in the future). When available it prints the aggregate report even for unhealthy sync. Its JSON output contains only aggregate lifecycle states, cursor presence, `sync` status/last-success timestamp/readiness, and `pendingProjectReconciliation` count—not tokens, room IDs, event IDs, message text, paths, or launch errors. A running service or established cursor alone is not proof of working Matrix intake. In a conversation, `!status` combines a typed live adapter snapshot with relay-authoritative manifest/runtime state: concept/kind, project and checkout labels, lifecycle and idle/busy state, adapter connection, generation ordinal/count, actual and saved/requested model and thinking, model mismatch, bounded context usage, pending queue counts, checkpoint state, redacted launch failure, and reconciliation count. The typed contract has no path, credential, prompt, tool-argument, output, or reasoning fields.

### One-time tmux socket cutover

Older deployments may have managed windows on `/tmp/tmux-$UID/default` while the interactive launcher uses `$XDG_RUNTIME_DIR/tmux-$UID/default`. Preview and clean up only those legacy windows during the deployment boundary:

```sh
printf '{}\n' | tmux_project managed legacy-window-preview
# Review every conversation, session, and window identity above.
systemctl --user stop pi-managed-session-relay.service
printf '{"confirmed":true}\n' | tmux_project managed legacy-window-cleanup
```

Cleanup derives the legacy socket from the current UID, verifies that it is a user-owned socket, and removes only windows carrying syntactically valid managed-conversation markers. It does not remove unmarked windows or sessions. After rebuilding/switching, start the relay and explicitly resume desired project conversations; the coordinator and resumed windows will then be created in the interactive runtime-directory server. Never run confirmed cleanup while the relay is active.

The relay uses bounded exponential backoff with jitter, honors Matrix `retry_after_ms`, and cancels waits on shutdown. Media is fetched through Matrix's authenticated client media endpoint; access tokens never enter media URLs, spool metadata, IPC, or Pi history. Stable Matrix transaction IDs make uncertain transcript, activity-card edit, checkpoint poll/notice, poll closure, notice, command-acknowledgement, and artifact-event retries idempotent. Typing is intentionally ephemeral and reconstructed only from live durable controls, command deliveries, or activity spans; it is never persisted as authoritative state. Artifact bytes cross IPC only as digest-verified bounded chunks, enter the private bounded spool, and use a durably recorded, expiry-bounded MXC reservation before retry-safe upload and room send; restart resumes the last durable phase and removes consumed local blobs. A crash in the create-response window can leave only an empty server-expiring reservation—never uploaded bytes—and durable export count plus spool quotas bound local recovery state. Checkpoint poll publication intent, exact answer mapping, event identity, and active/retired state are persisted before cursor advancement, so restart recovery preserves the hard boundary and cannot accept changed, duplicate, foreign, malformed, late, or post-close votes. Registry writes are private atomic write/fsync/rename operations. After relay restart, adapters may reattach during the reconciliation grace period; unmatched conversations become dormant. Accepted input, expanded input, persisted unfinished turns, checkpoints, and final projections resume from durable identity. Explicit stop/abort cancellation is terminal and is never recovered.

Cursor state is explicit: a fresh relay performs one bootstrap sync, persists its validated returned cursor, and does not inspect or execute retained timeline commands from that bootstrap response. A limited initial timeline is normal and does not block bootstrap. Established state requires a bounded cursor. Limited/oversized incremental timelines trigger forward `/messages` pagination from that saved sync token to the fixed new sync boundary. The relay recovers every affected room before dispatch, verifies the recovered history covers the sync tail, and preserves normal sender authorization and event identity deduplication. Recovery admits at most 512 events per room, ten pages of at most 100 events, and the existing 4 MiB response bound. Pagination must echo the requested `start` and terminate at the exact requested `end` boundary. An omitted `end` can also mean inaccessible history, so exhaustion alone is conservatively refused even if the visible sync tail is present. Pagination stalls, malformed/foreign/repeated events, unavailable or unprovable history and exceeded bounds leave the cursor unchanged with a concise journal diagnostic. Interrupted recovery starts again from the saved cursor; already accepted deliveries retain their stable identities. The relay never automatically skips an established gap. Authentication failures are concise HTTP diagnostics in the user service journal. Do not delete or hand-edit `registry.json`; restore the last known complete synchronized manifests and host-local registry together, or resolve the conflict explicitly. Legacy `.remote-session` files and rooms are never scanned or migrated.

### Persistent-state cutover and reboot recovery

`services.pi-harness.managedSessions.stateDirectory` defaults to
`%h/.local/state/pi-managed-sessions/relay` and is exported as
`PI_MANAGED_SESSIONS_STATE_DIR`. It contains `registry.json`, `activities.json`,
and `media-spool/`; custom raw-relay deployments also default project sessions
under this state directory. The NixOS module keeps project sessions, manifests
and the coordinator at their existing persistent locations. Do not synchronize
host-local relay state across hosts. `PI_MANAGED_SESSIONS_RUNTIME_DIR` remains
`$XDG_RUNTIME_DIR/pi-managed-sessions` for the socket and ephemeral
`sync-health.json` only. These must be separate non-nested directories.

On the first patched start, while holding the host lock, the relay copies any
existing legacy registry, activities, media spool and fallback project sessions
from the runtime directory into a private staging directory. It validates the
registry/manifest pair and atomically publishes the complete destination.
Credentials, sockets and transient observations are not copied. The source is
retained, not deleted; once the destination exists it is authoritative and the
legacy copy must not be used as current state. Failed staging is not adopted.
An incomplete destination, unsafe legacy files or a mismatched primary registry
fails closed for explicit recovery. A hard crash may leave a `.relocating-*`
staging directory; it is never used as a recovery source.

For a host already stuck at `bootstrap` after reboot:

1. Keep private backups of the legacy runtime directory and
   `~/.local/state/pi-managed-sessions/` before deployment. Coordinate a quiet
   relay when taking a consistent backup; never share the contents in chat.
2. Deploy the patched harness package/module together, then restart the relay.
   Editing a checkout alone does not update installed Nix store code. No token
   rotation, room replacement, registry edit or context reset is needed.
3. Check `pi-managed-session-status`: `sync.ready` should become true and the
   journal should stop repeating the bootstrap gap error. Send `!status` in the
   existing Matrix room, then one ordinary message to wake the saved session.
4. Review messages sent before bootstrap completed and explicitly resend any
   unfinished requests. That initial history is deliberately not executed.

If the old volatile registry was already lost on reboot, manifests preserve room
and Pi-session identity but cannot reconstruct all accepted-input, poll or
projection metadata. Do not claim those records were recovered. The persistent
cutover prevents that storage loss on future reboots, but cannot undo past loss.
For an **established** gap exceeding recovery bounds, preserve the cursor and
backups and arrange explicit history reconciliation; no reset-to-now CLI exists.
Repeated restarts, `!new`, or manually changing the cursor are not a safe fix.
Downgrading to the old runtime-directory launcher would reopen stale state and
is unsupported; rollback must restore a matched package and complete state set.

## Token rotation and device revocation

Rotation does not rebuild Pi sessions, recreate rooms, or clear registry/projection state:

1. Create a replacement Matrix login/device for the same configured bot MXID.
2. Atomically replace the SOPS-rendered credential file with exactly one `PI_MATRIX_ACCESS_TOKEN=<new-token>` assignment, owned by the relay user and mode `0400` or `0600`.
3. Restart and verify:

   ```sh
   systemctl --user restart pi-managed-session-relay.service
   pi-managed-session-status
   journalctl --user -u pi-managed-session-relay.service -n 50
   ```

4. Send one message to an existing managed room and confirm its normal projection.
5. Revoke the old Matrix device only after the replacement is healthy.

The launcher reads the credential file on every service start. Never put the token in Nix, shell arguments, tmux, Pi settings/session metadata, issue comments, test fixtures, or diagnostic commands. Errors and bounded diagnostics redact credential-like environment values and never include Matrix response bodies.

## Troubleshooting

Managed project windows inherit a service environment, not an interactive login shell. After direnv/project tools and the packaged runtime, their dispatcher appends conventional NixOS host tool locations: the user's legacy and XDG-state Nix profiles, the per-user system profile, global Nix profiles, wrappers, and the current system profile. This makes installed host tools such as zsh discoverable without sourcing shell startup files, importing credentials, or changing the shared tmux server's environment. Project executables retain precedence. Coordinator and ordinary interactive launchers do not receive this additional fallback. Existing running windows need a separately approved idle refresh after deployment to pick it up.

- **Service inactive:** inspect the user journal and credential owner/mode. Confirm linger is enabled and network-online is available.
- **HTTP 401/403:** replace or rotate the token and confirm the configured bot MXID did not change.
- **Repeated rate limits/outage:** leave the service running; bounded retry preserves cursor and stable transactions without duplicate turns.
- **Timeline gap:** limited bootstrap now establishes the cursor without replay. Established gaps recover within the documented bounds; an unrecoverable gap reports blocked sync and retains the cursor. Do not delete state or keep resending commands while it is blocked.
- **Dormant room:** ordinary text queues and wakes the exact persisted session. Dormant steer/abort intentionally do not wake it.
- **Launch failure:** verify the configured workspace root, immediate-child workspace, direnv policy, and `tmux_project` managed operations. Error output is intentionally concise and redacted.
- **Image rejected:** confirm the active model advertises image input and resend after selecting a capable model. For an actual Matrix download or model rejection, inspect that error or try another supported JPEG, PNG, or WebP. Stale or missing Matrix size metadata no longer causes rejection; the relay never sends only the caption.
- **Media spool quota:** let completed/expired deliveries and artifact exports clean up, then restart the relay. Never delete blob metadata referenced by a live pending input/export or hand-edit `registry.json`.
- **Artifact rejected:** pass a path relative to the workspace root, not the conversation's relative cwd. Hidden/control or sensitive paths, symlinks (including intermediate directories), special files, executable/active content, malformed media, and files over 25 MiB are deliberately unavailable. Linux descriptor-relative traversal pins every directory without following links. Outbound images undergo bounded ImageMagick decoding before IPC; decoding does not rewrite bytes, so upload size and digest describe the original file. The attachment acknowledgment supplies authoritative portable placement from the relay manifest, including when an external launcher forwards only the canonical workspace path. Missing host placement or workspace path disables export but does not disable checkpoints; update the host configuration and refresh the conversation.
- **Artifact delivery outage:** pending exports retry in the live relay with bounded exponential backoff and a per-attempt deadline, independently of other exports. Recovery does not block the IPC server starting. Permanent Matrix errors record a redacted terminal failure and emit an idempotent room notice; after fixing the media service, request a new export. No credentials, media URLs, paths, or server response bodies appear in that notice.
- **Malformed durable state:** stop the service and reconcile the complete manifest/runtime pair; temporary or legacy files are not recovery sources.

## Deferred scope

The current staged protocol deliberately excludes cross-host discovery, migration or failover; shared-room claims; inbound audio/video, encrypted media, generic inbound attachments, edits, reactions, and threads; container/sandbox isolation beyond the service and fixed launcher boundary; automatic project conflict prevention; idle process retirement; and import of legacy direct-bridge rooms or state.
