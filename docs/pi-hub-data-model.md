# PI Hub Data Model

## Goal

The hub needs one fast workstream-first view of:

- what workstreams exist
- which workstreams are currently processing or idle
- which projects or directories are attached to each workstream
- which attached projects are exposed into the agent VM
- which tmux sessions already exist and can be resumed

The primary unit is the workstream, not the project.

A workstream may:

- exist without any attached project
- attach zero, one, or many projects or directories
- attach the same project more than once through distinct worktrees
- run in parallel with other workstreams that touch the same project

Projects are scope hints and attachment targets. They are not the identity of
the session.

## Source Planes

### 1. Shared Project Plane

Host-managed source exposed into the guest VM:

- Path: `/home/beau/host/.pi-hub/shares.json`
- Source of truth: `agent-share` on the NAS host
- Semantics: security and exposure boundary

Each entry represents a directory intentionally bind-mounted into the shared
root and visible inside the VM.

### 2. Project Metadata Plane

Imported project metadata owned by each repo:

- primary source: repo-local `.pi/project.yaml`
- optional companion sources: repo-local `.pi/` files referenced by that
  manifest
- semantics: naming, tags, default branches, docs, and attachment hints

Project metadata helps the hub label contexts and offer attachment shortcuts. It
does not define workstream identity. The harness reads it directly from each
project rather than from a separate cross-project index.

Metadata import must degrade predictably:

- if `.pi/project.yaml` is missing, import falls back to "no repo metadata" for
  that project rather than failing the workstream row
- if `.pi/project.yaml` is unreadable, invalid, or schema-incompatible, import
  falls back to "invalid repo metadata" and surfaces an operator-visible error
- if a referenced companion file under `.pi/` is missing or invalid, the base
  metadata still imports and only that companion-backed shortcut is dropped with
  a warning
- incomplete metadata must not block path attachment; later implementation can
  decide which labels, tags, or shortcuts remain available from the successfully
  parsed subset

### 3. Workstream Plane

Guest-local durable workstream manifests:

- path: `~/.local/state/pi-harness/workstreams/`
- semantics: workstream identity, title, attached contexts, launch metadata,
  and operator intent

This plane is local to the machine and should not be versioned in git.

### 4. Runtime Plane

Guest-local live operational state:

- path: `~/.local/state/pi-harness/runtime/`
- semantics: tmux session names, live status, active model, last-seen time,
  last-processing time, and recent focus

This plane is local to the machine and should not be versioned in git.

## Merge Rule

Each row in the hub represents one workstream.

Each workstream row is a merge of:

- one durable workstream manifest
- zero or more project metadata entries
- zero or more shared project entries
- zero or one runtime status entry
- zero or one live tmux session

The key rules are:

- visible if a workstream manifest exists
- attachable to a project only if that project path is shared into the VM
- project browsing is a secondary index over attached contexts, not the primary
  list view
- a workstream may have zero, one, or many attached contexts with no required
  primary designation

## Identity Rules

### Workstream Identity

The canonical workstream key is a local, stable `workstreamId` generated by the
harness when the workstream is created.

Recommended shape:

- short slug from the title
- plus a disambiguating suffix when needed

The workstream keeps the same id even if:

- its title changes
- attached projects are added or removed

### Context Identity

Each attached context has a stable `contextId` within the workstream manifest.

If the context points at a project with imported metadata, it may also carry
`projectId`. Directories without project metadata remain valid contexts and are
identified only by path.

The same `projectId` may appear multiple times in one workstream if the paths
are distinct.

## Core Records

### SharedProject

Represents one host directory exposed into the VM.

Fields:

- `agentPath`: share key relative to `/home/beau/host`
- `sourcePath`: original host path
- `hostPath`: host-side mounted path under `/home/beau/agent`
- `guestPath`: guest-visible path under `/home/beau/host`

### ProjectMetadata

Represents imported project metadata.

Fields:

- `id`
- `name`
- `defaultBaseBranch`
- `repoPath`
- `metadataFile`
- `toolingFile`
- `notesFile`
- `active`

### WorkstreamContext

Represents one path attached to a workstream.

Fields:

- `contextId`
- `projectId` optional
- `displayName`
- `path`
- `kind` (`worktree`, `checkout`, or `directory`)
- `mode` (`isolated`, `shared-readonly`, or `shared-readwrite`)
- `branch` optional
- `ownerWorkstreamId` optional

Mode semantics:

- `isolated`: the path belongs to this workstream only
- `shared-readonly`: another workstream may observe the same path without
  editing
- `shared-readwrite`: multiple workstreams intentionally point at the same path
  and see live file changes immediately

### WorkstreamRecord

Represents one durable workstream manifest.

Fields:

- `workstreamId`
- `title`
- `tmuxSession`
- `createdAt`
- `updatedAt`
- `contexts`
- `notes`

### RuntimeStatus

Represents guest-local live state for one workstream.

Fields:

- `workstreamId`
- `state`
- `cwd`
- `lastSeenAt`
- `lastProcessingAt`
- `activeModel` optional

### HubWorkstreamRecord

The merged row shown in the hub.

Fields:

- `workstreamId`
- `title`
- `tmuxSession`
- `status`
- `contexts`
- `sharedContexts`
- `projectMetadata`
- `lastSeenAt`

## Initial Status Model

Start simple:

- `processing`
- `idle`
- `dead`
- `unknown`

For the first UI, `idle` can be rendered as "waiting".

The status contract is:

- `processing`: the Pi CLI is currently handling a prompt or tool loop
- `idle`: the session exists but Pi is not currently processing
- `dead`: the workstream manifest exists but the tmux session no longer does
- `unknown`: runtime state is missing, unreadable, or schema-incompatible while
  the tmux session still exists, or the newest trusted runtime record is older
  than 12 hours

For v1, only `processing` and `idle` need to be written directly. `dead` and
`unknown` should be derived by the Go harness when it merges runtime files
with tmux session discovery.

Do not block on smart inference beyond this. A small runtime state file written
through a thin Pi lifecycle integration is enough for v1.

## Context Isolation And Sync

The default for git-backed project attachment should be an isolated worktree.

This gives:

- branch isolation
- safer parallel work on the same project
- simpler cleanup and ownership

Shared live state is also allowed, but only through explicit shared modes.

Sync expectations:

- isolated contexts sync through normal git operations and committed work
- shared contexts stay in live sync because they point at the same path
- uncommitted live sharing is an advanced workflow and should remain opt-in

## Discovery Order

1. Read `shares.json`.
2. Read repo-local project metadata.
3. Read durable workstream manifests.
4. Read runtime state files.
5. Inspect tmux session existence.
6. Produce merged `HubWorkstreamRecord[]`.

## Context Label Precedence

When the harness needs one operator-visible context label for `ph list`,
`ph menu`, or attach-time shortcuts, it should derive that label in this order:

1. explicit context `displayName` already stored in the workstream manifest
2. repo-local project metadata `name` for the attached repo
3. shared-project registry `agentPath` for the attached guest path
4. the attached path basename

Additional rules:

- `projectId` helps correlate records but does not supply a label by itself
- a higher-precedence label wins even if a lower-precedence source disagrees
- missing or invalid repo metadata skips step 2 and falls through without
  blocking the attachment
- shared-project data labels only guest-visible paths that actually match the
  share registry entry
- when two contexts resolve to the same final label, the harness should keep
  both attachments and disambiguate in the surrounding row output with path or
  mode details rather than inventing a different base label

### Worked Examples

#### Plain Path With No Share And No Repo Metadata

Attached context:

- path: `/home/beau/host/scratch/notes`
- manifest `displayName`: unset
- share-registry match: none
- repo metadata: missing

Result:

- context label: `notes`

Reason:

- there is no stored label, no project metadata label, and no share label, so
  the basename fallback wins

#### Shared Project Without Repo Metadata

Attached context:

- path: `/home/beau/host/projects/pi-harness`
- manifest `displayName`: unset
- share-registry match: `projects/pi-harness`
- repo metadata: missing

Result:

- context label: `projects/pi-harness`

Reason:

- repo metadata is absent, so the harness falls through to the share-registry
  label instead of the basename `pi-harness`

#### Repo With Metadata Overrides Share Label

Attached context:

- path: `/home/beau/host/projects/pi-harness`
- manifest `displayName`: unset
- share-registry match: `projects/pi-harness`
- repo metadata: `id: pi-harness`, `name: Pi Harness`

Result:

- context label: `Pi Harness`

Reason:

- repo metadata outranks the share-registry label, so the operator sees the
  repo-local project name instead of the share key

#### Explicit Manifest Label Overrides Repo Metadata

Attached context:

- path: `/home/beau/host/projects/pi-harness`
- manifest `displayName`: `Harness CLI`
- share-registry match: `projects/pi-harness`
- repo metadata: `name: Pi Harness`

Result:

- context label: `Harness CLI`

Reason:

- once a context stores an explicit `displayName`, later metadata imports do
  not rewrite that operator choice

#### Conflict Example: Two Contexts Resolve To The Same Metadata Name

Attached contexts:

- `/home/beau/host/projects/pi-harness` with repo metadata `name: Pi Harness`
- `/home/beau/host/projects/pi-harness-alt` with repo metadata `name: Pi Harness`

Result:

- each context keeps the base label `Pi Harness`
- list or menu rendering adds surrounding disambiguation from path, branch, or
  sharing mode when needed

Reason:

- the precedence rule answers which source names the context; it does not force
  the harness to mutate one context label just because another context resolved
  to the same name

#### Missing-Metadata Example: Invalid Repo Metadata Falls Back Cleanly

Attached context:

- path: `/home/beau/host/projects/pi-harness`
- manifest `displayName`: unset
- share-registry match: `projects/pi-harness`
- repo metadata: invalid `.pi/project.yaml`

Result:

- context label: `projects/pi-harness`
- operator-visible warning: repo metadata is invalid

Reason:

- invalid metadata drops out of the precedence chain for labeling, but the
  attachment remains valid and still uses the next-best share-derived label

## First Commands Supported By This Model

- `ph menu`
- `ph new <title>`
- `ph list`
- `ph list --json`
- `ph attach <workstream>`
- `ph status <workstream>`
- `ph add-context <workstream> <path-or-project>`

## Deliberate Non-Goals For Phase 1

- editing repo-local project metadata from inside the harness UI
- automatic Loom orchestration
- automatic project inference from shell history or prompt contents
- perfect waiting-for-input detection beyond "Pi is not processing"
- replacing tmux as the underlying session transport
